# Design decisions

Key design decisions in planprice, each with the reasoning and what it would cost if it turned out wrong, in the format
`<decision> — <why> — <cost if wrong>`.

- Prices come from an embedded, checksummed snapshot of the public AWS Price List Bulk API, not a live API — estimates must be reproducible and work offline without credentials; the Query API needs credentials — prices go stale between refreshes; mitigated by `snapshot info` (offer versions) and a documented refresh procedure.
- Snapshot covers us-east-1 and eu-west-1 only — two regions are enough to exercise region resolution end to end while keeping the refresh (two ~450 MB EC2 streams) and the embedded file (1.8 MB) small — users in other regions get `price-not-found` components plus a warning until a region is added (a documented three-step change).
- The EC2 offer files (~480 MB and ~440 MB) are streamed through a filter and never written to disk — the build machine has little free disk and the repo avoids storing datasets over 200 MB; only the ~4 MB slim subset is cached (git-ignored) — about 1 GB is transferred per refresh; if the transfer itself were unacceptable the alternative is AWS's per-page pricing JSON, which is undocumented.
- Two-stage refresh (fetch -> slim offer files, build -> snapshot) — selection rules can be iterated offline, and slim files double as test fixtures — slim files must be re-fetched if a coarse filter is widened.
- Usage types are normalised by stripping the region's prefix (`EU-`, `USE1-`) using an explicit region table, not a regex — a regex like `^[A-Z]+-` would also strip real usage types such as `TS-LoadBalancerUsage` — each new region needs a table entry.
- Conflicting duplicate products abort the build; identical duplicates collapse to the lowest SKU — silently picking one of two different prices would produce wrong estimates — a future AWS data quirk can block a refresh until a rule is tightened.
- Exact `big.Rat` arithmetic, rounding only at display time — prices go to 10 decimal places and Lambda/S3 quantities reach billions — about 3,800 allocations per 15-resource estimate; irrelevant at this scale (125 µs).
- A month is 730 hours — this is the convention AWS uses in its own calculator — months with 744 hours are under-estimated by 1.9%.
- Free tiers are not deducted (Lambda 1M requests / 400k GB-s, S3, etc.) — they are per account, not per resource, and a PR estimate cannot know what else the account uses — small workloads are over-estimated.
- Volume tiers (S3 Standard storage bands, Lambda duration bands) are applied per resource — the plan does not reveal account-wide usage — large accounts are over-estimated slightly; documented in Limitations and per mapper.
- Usage-based components with no usage value are excluded from totals and listed, rather than assumed to be zero or a default — a silent default would make totals look precise when they are not — totals are lower bounds until a usage file is supplied; every output says so and `usage-template` generates the file.
- Usage files are YAML with precedence type defaults < longest `[*]` pattern < exact address, merged key by key — mirrors how teams think ("all workers do X, this one does Y") — a mistyped address silently matches nothing; mitigated by warning on entries that match no plan resource and erroring on unknown keys.
- Unset/unknown EBS volume type is priced as gp2 and an unknown root-volume size as 8 GB — gp2 is the EC2 API default; 8 GB is the size of common Amazon Linux AMIs — AMIs with gp3 or larger root volumes are mis-priced by a few dollars; the breakdown labels the assumption.
- Unset RDS `storage_type` is gp2 (io1 when `iops` is set) — matches the RDS API default — plans using newer defaults may be mis-priced; visible in the component name.
- RDS gp3 baseline is 3,000 IOPS / 125 MiB/s below 400 GB and 12,000 IOPS / 500 MiB/s from 400 GB — AWS documentation for MySQL, MariaDB and PostgreSQL — wrong for engines planprice does not price anyway.
- t3/t3a/t4g instances default to unlimited CPU credits, t2 to standard — AWS launch defaults; surplus credits are a usage-based component — t8i and other new burstable families are not modelled (no credit component).
- Only Linux and Windows on-demand, shared-tenancy instances are priced; OS comes from the usage file (default Linux) — the plan does not reveal the AMI's OS — Windows instances are under-priced unless the usage file says `operating_system: windows`.
- S3 Glacier Deep Archive is not offered as a storage class — its storage price is in a separate offer file (`AmazonS3GlacierDeepArchive`) that the snapshot does not include — users must price Deep Archive elsewhere; the usage validator rejects the class name so it is never silently zero.
- `aws_eip` is reported as unsupported, not free — since 2024 public IPv4 addresses cost $0.005/hour — reports list it as unsupported rather than under-stating cost.
- Diffs match components by stable keys (`instance`, `root_block_device/storage`), not names — an instance-type change should read as one changed line — keys must stay stable across releases or old JSON reports stop lining up.
- `--fail-above-percent` ignores a zero base cost — a percentage of zero is undefined — a brand-new stack can only be gated with `--fail-above-increase`.
- Plans are generated with real Terraform 1.15.8 and hashicorp/aws 6.68.0 against a provider block with static fake credentials and every credential/account check skipped, and committed as JSON — `plan` for create-only configs without data sources makes no AWS API calls; committing JSON keeps tests offline — no committed plan contains updates against real state; that path is covered by a hand-written synthetic plan instead.
- Go 1.25 language level, one third-party dependency (`go.yaml.in/yaml/v3`) — YAML is the natural usage-file format; everything else is standard library — the dependency must be kept patched.
- No Docker/integration target — nothing in planprice talks to a service at estimate time; `scripts/gen-plans.sh` (network + Terraform) is the only external integration and is run by hand — regenerated plans are not verified automatically in CI.
